# ADR-007 — Provider adapters and capability registry

Providers declare capability, price, limits, health, region and credential reference. Adapters normalize submit, poll, cancel, callback and result into durable provider jobs. Domain plans never contain vendor-specific types.

Routing considers policy, rights, region, health, quality and cost and records rejected alternatives. Fake adapters simulate success, delay, rate limit, transient and permanent failure; fallback changes provider without changing the domain brief.

Capabilities additionally declare a completion mode — `synchronous`, `polling`, `webhook` or `both` — and an explicit `supportsCancellation` flag, both truthful per adapter. A synchronous provider (ElevenLabs TTS) returns a discriminated `completed` submission carrying the finished result bundle plus the provider's own reference for the effect; the durable ProviderJob still records every state transition, and the worker short-circuits polling and retrieval because both would be fabrications. An asynchronous provider (HeyGen) returns `accepted` with a provider job id. The worker fails closed at the planned tick when a declared capability lacks its method (polling without `getStatus`/`retrieve`, cancellation without `cancel`, webhook without `verifyWebhook`), so false capabilities can never reach a paid effect. Apollo-side idempotency (composite unique key plus request fingerprint) never depends on the provider's own `supportsIdempotency`; that flag only states whether the upstream API deduplicates retried submissions. Every adapter exposes a versioned identity — `id`, `adapterVersion`, optional `modelRef` and a `configHash` computed from non-secret configuration only — persisted with each result artifact for lineage.
