# ADR-003 — Object storage and content addressing

Use an S3-compatible adapter: filesystem/MinIO in development and managed object storage in preview/production. SHA-256 is streamed during multipart upload; the canonical key is scoped by content digest, while workspace references retain independent rights.

Masters and derivatives use separate immutable prefixes. Short-lived signed URLs are issued only after authorization; lifecycle rules move cold masters without changing identity. Completion verifies part hashes, size and final checksum. Dedupe may reuse bytes globally but never rights, metadata or access across workspaces.

For project proxy and final-export outputs, the SHA-256 of the bytes proves content integrity but does not define the logical artifact. Two projects may legitimately render byte-identical media while retaining different reserved artifact IDs, manifests and lineage. Their storage prefix is therefore the first 32 lowercase hexadecimal characters (128 bits) of the canonical SHA-256 of `[kind, outputArtifactId]`, where `kind` is exactly `editorial-proxy` or `final-export`; the full byte SHA-256 remains in the content-addressed key. The prefix is deliberately opaque, rejects empty or whitespace-bearing IDs instead of normalizing them, and makes retries for the same reserved ID converge while keeping different IDs and kinds independent.

This changes physical-key derivation without a compatibility fallback. At production cutover, `project-proxy-render` and `project-final-export` queues must be quiescent: no operation may be `queued`, `running`, `waiting` or `retrying`. A persisted attempt created under the previous derivation must finish or be handled explicitly before deployment; it must not be silently replayed across the boundary. The supervised preflight reads the canonical `public_operations` table and fails closed before deployment mutation when any such operation exists.

The local MinIO dependency uses the upstream registry shown by the [MinIO repository instructions](https://github.com/minio/minio/blob/0d7408fc9969caf07de6a8c3a84f9fbb10a6739e/README.md): `quay.io/minio/minio`. Compose pins the unchanged signed source release [`RELEASE.2025-04-22T22-12-26Z`](https://github.com/minio/minio/releases/tag/RELEASE.2025-04-22T22-12-26Z) and its Quay multi-platform index digest `sha256:a1ea29fa28355559ef137d71fc570e508a214ec84ff8083e39bc5428980b015e`; that index publishes Linux manifests for amd64, arm64 and ppc64le. Both MinIO services must use the same tag-and-digest reference. The source-tag signature does not assert a separately verified container-image signature; the immutable registry digest is the image identity enforced here.

The render worker selects `local` or `s3` through an explicit composition-root setting. The S3 adapter first rechecks the workspace-scoped artifact projection in Postgres, then performs `HeadObject` with checksum mode enabled. Materialization fails closed unless byte size, a full-object SHA-256 (native checksum or `x-amz-meta-apollo-sha256`) and a non-null immutable `versionId` match the protected `RenderInput`. Only then may it create a SigV4 GET URL bound to that exact version. The configured maximum TTL is 30–300 seconds; the effective TTL is recomputed immediately before signing and shortened so the URL can never outlive the materialization authorization. An expired authorization prevents even the storage probe. The URL remains inside the non-serializable worker lease and is never returned by a public capability.

S3-compatible development endpoints may use plain HTTP only on loopback or on a single-label isolated Compose service with explicit `APOLLO_V2_S3_ALLOW_INSECURE_HTTP=true`. A dotted/public hostname and every production endpoint must use HTTPS even when that flag is present. This follows the AWS contracts for [SigV4 query authentication](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-query-string-auth.html) and [HeadObject checksum mode](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html). Promotion requires SHA-256, exact byte size and a non-null object `VersionId`; worker materialization revalidates that immutable version into operation-owned ephemeral storage before FFmpeg/Remotion receives a path or signed URL.
