# ADR-159 — Host safety gate, serial deploy and worker shutdown

## Status

Accepted for implementation on branch `claude/wave23-runtime-safety` (Wave 23, 2026-09-18/19). Implemented and integrated on the branch; tested where the evidence section says so; **not deployed and not accepted by the owner**. Nothing in this ADR authorises a production deploy, a resumption of the paused Apollo fleet, or access to the shared VPS.

## Context

`AGENTS.md` ("Operação segura da VPS Hostinger de produção") states binding operational rules — CPU busy and steal measured separately, one mutable operation and one owner at a time, one container at a time with verified identity, aggregate resource limits with margin for the host's other services, preflight 60 s / monitoring every 10 s / postflight 60 s, an incident latch released only by the owner and followed by five stable minutes — and says in so many words that no runtime monitor implemented them.

The Gate Zero inventory of this wave confirmed it: `infra/deploy/apollo-vps.sh` stopped every container with `docker stop … || true` and `docker rm … || true`, then started the fleet with 19.5 CPUs of quotas on a 4 vCPU host; no code read `/proc`, `pg_stat_activity` or `max_connections`; the health route returned a static `{status:'ok'}`; three of the nine continuous workers stopped on a boolean flag checked once per loop, the render worker's five-claim chain never received a signal (its best-fenced branch could not be reached by SIGTERM at all), and `PrismaClient` opened backends without `application_name`, so a stopped container could not be told from a reconnecting one — the mechanism of the 29 July 2026 orphan-connection incident.

## Decision

1. **Host orchestration stays in bash; decisions run in Node inside the image.** The VPS host is assumed to have bash and docker but not Node (the deploy already validated configuration with `docker run --rm IMAGE node -e`). `infra/deploy/apollo-vps.sh` and `infra/deploy/lib/*.sh` keep every host effect (lock, stop, rm, run, inspect). Every judgement — the host-safety verdict (`scripts/ops/host-safety-verdict.mjs`), the resource budget (`scripts/ops/resource-budget.mjs`), the sampling monitor (`scripts/ops/host-safety-monitor.mjs`) — runs as a short-lived or run-scoped container built from the Apollo image, so the numbers are computed by tested TypeScript, never re-derived in shell. The runtime image therefore ships `config/` (the policy catalog and the resource budget) next to `scripts/` and `src/`; the first run against a real daemon (CI run 35450914276) found it missing and the Dockerfile was corrected.

2. **Operational state is host state, never product state.** `APOLLO_OPS_STATE_DIR` (`/var/lib/apollo-ops` on the host, mounted read-only at `/app/ops-state` in every Apollo container) holds only `gate.json`, `latch.json`, `lock/owner.json` and `journal/`. Jobs, operations, versions and artifacts remain exclusively in PostgreSQL; no application service reads the state directory. Its formats are specified in `docs/specs/11-host-safety-and-serial-operations.md`; the bash writers and the TypeScript readers are proven against the same fixtures.

3. **Fail closed, in every direction.** A gate file that is absent means no operation is in progress (open); a gate that is malformed, closed, of unknown schema or older than its `ttlMs` is closed; a latch outranks every metric and survives container restarts and reboots because it lives on the host; thresholds and observation values the catalog does not declare close the gate (`policy-unconfigured`) instead of receiving a default; a monitor that dies or falls behind closes the gate; a health probe answering 200 is one input and never proof of host health; a sample that is missing, stale, malformed, out of order or from a clock that moved backwards closes the gate. Windows are measured in elapsed monotonic time, not counted in samples: three fast samples are twelve seconds of coverage, not a preflight.

4. **The gate controls admission only.** Workers read the gate between claims (and before each of the render worker's five branches) through `src/v2/application/ports/admission-gate.ts` / `src/v2/infrastructure/ops-state/file-admission-gate.ts`; a closed gate means no new claim and an idle poll, never an exit. Work already admitted is bounded by SIGINT/SIGTERM through one AbortController per process (`src/v2/application/worker-lifecycle.ts`), by a shutdown grace deadline below the container stop timeout (`APOLLO_V2_WORKER_SHUTDOWN_GRACE_MS`, default 20 000 ms, ceiling 29 000 ms, exit code 2 when the deadline expires), and by the run's own child handles (`terminateChild`: SIGTERM, then SIGKILL after the grace, then the real `exit` event). Nothing scans the host for processes.

5. **A graceful shutdown is neither a failure nor a cancellation.** An interrupted PublicOperation attempt is reported by the worker as the retryable failure `worker_shutdown` with `nextAttemptAt` one millisecond after the failure; the domain turns that into `retrying` with the lease **and the error** cleared — claimable by another worker immediately, attempt fence intact, no promotion possible for the lost attempt. On the row, therefore, a shutdown hand-back is recognisable by its immediate schedule (no exponential backoff), not by a code: measured in CI run 35450914276 as `{status: retrying, attempt: 1, leaseOwner: null, errorCode: null}` after a SIGTERM delivered while the row was `running/rendering`. The `worker_shutdown` code is persisted only when the final attempt dead-letters (`failed`), exactly where lease expiry would have written `worker_lease_expired`; the existing manual retry route is the recovery. Provider jobs keep the `submitting` ambiguity fence unchanged: a shutdown never resubmits a paid request. Capture-sync runs that are abandoned mid-correlation recover by lease expiry (its repository has no release); the director branch settles rather than aborts (it has no abortable port); webhook delivery HTTP is bounded by the shutdown deadline only.

6. **One explicit aggregate budget.** `config/resource-budget.json` resolves a profile into per-container quotas (`--cpus`, `--memory`, `--memory-swap` equal to memory, `--pids-limit`) whose sum — app, enabled workers, the concurrent monitor and the largest sequential auxiliary — must fit an envelope that itself fits the host. The `shared-production` profile declares no quota; it requires an operator-approved document (`apollo-resource-budget-approval/v1`) that leaves at least 25 % of the host CPUs and 2 GiB of memory for the host's other services. Missing, unlimited, NaN, negative or over-budget values are refused with reasons before the first mutation. After each `docker run` the deploy reads `HostConfig.NanoCpus|Memory|MemorySwap|PidsLimit` back and treats a mismatch as inconclusive. cgroup v1 or a daemon warning about missing limit support refuses to deploy. Daemon-side work — `docker load`, `docker pull`, image decompression, hashing, backups — runs outside every container cgroup, so it is declared `uncoveredHostWork`: the deploy never performs it, and on the shared profile the image must already be present.

7. **Identity by labels, confirmation before the next step, no rollback.** Containers carry `apollo.managed=true`, `apollo.role=<role>`, `apollo.deployment=<runId>`. A container without them blocks the deploy before anything is touched (no latch, because nothing is half done) and must be adopted explicitly with `--adopt-unlabelled <name>`, which journals the inspected image and networks. Each replacement, one container at a time, in the order app → workers: identity → `docker stop --timeout 30` → `.State.Status` ∈ {exited, dead} → `.State.Pid = 0` → zero PostgreSQL backends for `apollo-video-<role>` in the monitor's samples → `docker rm` (absence re-confirmed) → `docker run -d` with labels, quotas, the read-only state mount and `APOLLO_PROCESS_ROLE` → limit readback → health → gate re-read. Any ambiguity ends the step as `step-inconclusive`: the latch is engaged, the journal keeps the first cause, nothing else is stopped, no retry is stacked and no container is started as a "rollback". A timeout without confirmation is an inconclusive result, never a success by absence of a readable error.

8. **The operation is exclusive and journaled.** `lock/` is an atomic `mkdir` whose `owner.json` records run id, PID, boot id and start; an existing lock is taken over only when its boot id differs or its PID is gone and it is older than ten minutes — never by age alone. Every step writes one line to `journal/<runId>.ndjson` (the monitor writes its samples to `journal/<runId>.monitor.ndjson`, one writer per file); no environment value is ever journaled or printed. `plan` performs no mutation and writes no journal line.

9. **Test seams are declared and refused in production.** Shortened windows, an external monitor, a substitute policy catalog and the other knobs used to prove the sequence in seconds exist only for `isolated-ci`/`local-dev`; the shared profile refuses them.

## Consequences

- A production deploy takes longer (one container at a time, 60 s preflight and postflight) and refuses more often; both are intended. With the shipped catalog a production deploy refuses today with `policy-unconfigured`, because `sampleFreshnessMs`, `healthLatencyMs` and `oomRecentWindowMs` are the owner's call and were not invented here.
- OOM coverage is honest but partial: OOM kills of Apollo containers (`State.OOMKilled`) plus kills observed inside the run's window. Host-wide kernel-log detection is not implemented.
- The Compose workflow used by CI and local development is not driven by `apollo-vps.sh`; its services receive no gate and no quotas from this wave. That path is documented as uncovered.
- Workers behind a stale gate stop admitting work until an operator runs `apollo-vps.sh gate open --reason …`; this is the accepted cost of a monitor that died mid-operation.
- Webhook delivery HTTP remains non-abortable; the director branch settles rather than aborts; capture-sync recovery after a hard kill remains lease expiry. All three are bounded by the shutdown deadline and the container stop timeout.

## Evidence

Recorded in `docs/REQUIREMENTS-TRACEABILITY.md` (FR-232, FR-236 rows and the Wave 23 note) and in the wave's draft PR. In summary: policy, collector, state files, lock/latch/gate, budget and worker lifecycle are proven by unit suites under `npm test`; the deploy sequence is proven against a recording fake Docker; real containers, a sentinel, stop confirmation and limit readback are proven only in the CI job "Isolated Compose infrastructure"; worker interruption and resume journeys run against a throwaway PostgreSQL with real workers and FFmpeg; metric anomalies are injected at the collector boundary and are not measurements of the Hostinger host.
