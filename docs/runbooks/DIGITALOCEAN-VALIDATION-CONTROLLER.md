# Coordenador local one-shot — validação descartável DO (W27/W28)

Este script é um owner local para uma única rodada aprovada; não é serviço, aprovação de deploy, aceite W27/W28, nem garantia de custo/remoção quando a API/SSH falha. Não usa Hermes nem depende da sessão de chat. A instalação e o probe de uma tarefa real do Windows Task Scheduler, com conta operacional e execução independente do chat, pertencem à revisão da Astra; **não** são feitos por este script. O computador Windows ligado e a tarefa viva continuam pré-requisitos. O controlador não sobrevive a desligamento/crash do computador e não reinicia automaticamente uma rodada incerta.

**Condição da rodada W27/W28, autorizada pelo proprietário em 30/09/2026:** executar nesta máquina mantendo Windows ligado e logado, após o CI passar. O registro S4U foi negado (`0x80070005`); não houve elevação nem mudança de política para contornar a negativa. Os probes em modo `Interactive` comprovaram independência do processo invocador/chat, autenticação Brain/GET da conta DO e execução real do CLI `--check`, não sobrevivência a logout. A execução supervisionada mantém prevenção de suspensão automática enquanto o processo está vivo; isso não impede logout, suspensão forçada ou desligamento. Fora dessa janela expressamente autorizada, não presumir que esse modo basta para outra rodada.

**Decisão adicional do owner em 30/09/2026:** “Autorizar NYC3 com os mesmos limites e isolamento”. O único par adicional permitido ao controlador é `nyc3` + `s-8vcpu-16gb-intel`; o par anterior `nyc1` + `s-8vcpu-16gb-amd` permanece válido. Não cruzar planos/regiões nem tentar fallback automático. O preflight real anterior, sem criar recursos, rejeitou NYC1 por indisponibilidade dos planos 8/16; o preço de US$ 0,16667/h e a disponibilidade NYC3 foram informados para aquela consulta, não são garantia de preço/estoque futuros. Astra deve verificar novamente os dados pela API, confirmar que a VPC default NYC3 preexistente não tem membros antes de usá-la, e não criar/remover VPC. Limites inalterados: até 4 h/US$ 1, 8 vCPU/16 GiB, snapshot preservado, isolamento de produção, sem DNS ou providers pagos. Esta alteração local não autoriza execução real por Sol; toda operação real cabe à Astra.

## Bloqueios antes do `--execute`

1. Aplicar AGENTS.md e o runbook `DIGITALOCEAN-DISPOSABLE-VALIDATION.md`; conferir autorização vigente e escopo desta rodada (somente par NYC1/AMD ou NYC3/Intel, descartável, 8 vCPU/16 GiB, até 4 h/US$ 1, snapshot preservado, deleção), gates locais/CI Linux, evidência editorial exigida e o estado de produção. Nada neste controlador cria autorização nova.
2. Preparar `source.tar` **fora do repositório** com `prepare_bundle.py`, de HEAD revisado e tracked limpo. O SHA do bundle e os SHA-256 dos três arquivos de tool enviados (`remote_guard.py`, `batch.sh`, `Dockerfile.runner`) devem ser revisados e gravados na config. O script recusa divergências; config.example.json contém placeholders deliberadamente inválidos.
3. Usar exclusivamente `C:\Users\<operador>\AppData\Local\apollo-validation` como `evidence_root`; criar previamente diretório privado e conferir ACL real no Windows. A chave SSH registrada, config, loader e bundle são caminhos privados absolutos fora do repo. `safe_path` exige a grafia nativa canônica: no JSON Windows escrever barras escapadas (`C:\\Users\\...`); nos argumentos CLI usar o caminho Windows entre aspas (`'C:\Users\...'` em Git Bash/PowerShell). A variante `C:/...` é recusada nesse contrato, mesmo quando outro programa Windows a aceita; não enfraquecer o validador nem normalizar entradas inválidas silenciosamente. Todos os operadores concorrentes devem usar o mesmo lock nesse diretório, incluindo watchdog. Nunca remover o lock ou um intent para liberar retry.
4. Instalar localmente Python >=3.12 em venv isolado com `scripts/ops/digitalocean-validation/requirements.txt` (pins paramiko 5.0.0 e cryptography 50.0.1; CI instala wheels binárias no `runner.temp`, sem depender dos pacotes do runner). Confirmar compatibilidade no venv local antes de executar; os testes Windows existentes com Python global não validam esses pins. Confirmar o login SSH por chave pública DO registrada, fingerprint exato, IP CIDR /32 público do operador, VPC e snapshot autorizados. Loader aprovado é módulo Python privado com `load_token() -> str`, passado somente a `--execute`; não use variável de ambiente nem argumento com valor do token. O controlador não implementa consulta ao Brain.
5. Task Scheduler: Astra deve testar uma tarefa inofensiva que sobreviva ao fim do processo que a lançou; configurar conta, ACL, diretório de trabalho, log local, prazo e comportamento de logout antes de qualquer VM. Não inferir continuidade da tarefa da existência de `schtasks`.

Comandos locais, após preencher e proteger a config real (o exemplo não passa):

    python C:/dev/apollo-video/scripts/ops/digitalocean-validation/controller.py --check --config 'C:\Users\leand\AppData\Local\apollo-validation\run-config.json'
    python C:/dev/apollo-video/scripts/ops/digitalocean-validation/controller.py --execute --config 'C:\Users\leand\AppData\Local\apollo-validation\run-config.json' --token-loader 'C:\Users\leand\AppData\Local\apollo-validation\approved-loader.py'

`--check` verifica schema, paths, SHA do bundle e SHA dos tools; não importa loader, não lê chave privada e não consulta rede. `--execute` importa loader somente após check e adquire lock OS não bloqueante antes do primeiro GET. Se o run directory já existir, aborta; não faz resume, segundo POST, segundo SSH nem limpeza automática em estado incerto. É deliberadamente one-shot: intervenção do owner é necessária após crash/timeout. O JSON único de stdout é resultado do CLI; `controller.jsonl`, intents, manifesto, postflight, amostras e evidência visual ficam no run directory privado fora do repo.

## Estado e autoridade

- `started` / `inventory_verified`: sem mutação; inventário paginado completo deve não conter nenhum droplet Apollo (inclusive ambíguo). Conta com Apollo em produção bloqueia por segurança; não há exceção inferida. Consulta preço/hora atual do tamanho, 8 vCPU/16384 MiB, disponibilidade na região configurada, snapshot, VPC da mesma região e chave/fingerprint antes de criar. A checagem de membros da VPC default NYC3 é pré-requisito manual da Astra, não implementada pelo controlador.
- `tag_verified`, `firewall_verified`, `droplet_verified`: POST único com intent fsync antes da chamada; GET posterior confere ID/nome/tag/VPC/plano/região/imagem/created_at. Firewall permite somente SSH do /32 configurado, sem IPv6; tráfego de saída IPv4 para dependências de build. Droplet Ubuntu 24.04 fresh, `backups=false`, `ipv6=false`, `monitoring=false`, `dns=null`, nenhuma criação de snapshot/volume/DNS/provider pago. O snapshot preexistente nunca recebe DELETE.
- `ssh_pinned`: host key ED25519 única por run gerada em área privada e injetada no cloud-init `ssh_keys` (sem token); Paramiko RejectPolicy usa a chave gerada para pinning. Login usa chave SSH privada local já aprovada cujo public key/fingerprint bate com a chave DO, sem agent, AutoAddPolicy ou cópia da chave. TCP readiness inicial é limitada e anterior ao handshake; depois do primeiro handshake qualquer perda vira unknown sem segundo canal operacional/retry.
- `guard_exited`: um Transport SSH contém o canal do guard e o canal SFTP; o SFTP permanece aberto para transferências exigidas pelo próprio guard. Esta é a sobreposição mínima de canais do **mesmo** transporte, não duas conexões SSH nem outro owner. `remote_guard.upload()` real anuncia `upload_ready` e exige `source.tar` + `upload.complete` via SFTP no root do run. Não recebe `source.tar.gz` via stdin: mantemos stdin do canal vivo até exit/postflight. Enviar tar em stdin contrariaria o protocolo do guard neste commit. Bytes e SHA são lidos de volta antes do marker; hash/HEAD ainda são revalidados pelo guard.
- `deleted_verified`: `postflight.json` e `samples.jsonl` são leitura obrigatória pelo SFTP original; PID/deadline são copiados do owner record remoto observado, sem síntese. Falha/inconclusão da prova impede delete. A coleta editorial é independente e registra `visual-inventory.json` com `collected`, renders, `acceptance.status`, `missing` e `errors`; sua falha não autoriza delete nem impede delete se, e somente se, o watchdog demonstrar `terminal_ready()`. Fechar SFTP/SSH, então apresentar ao watchdog o manifesto candidato released e validar proof. Reusar `watchdog.run(mode='delete')` com **empréstimo do lease OS já adquirido**: verifica path/estado do lock e mantém a aquisição externa até GET 404 de droplet/firewall/tag + snapshot presente. Intents do watchdog previnem reenvio de DELETE após ambiguidade. O resultado distingue `work_outcome`, `acceptance` e `cleanup_outcome`; o CLI sai com código 1 em falha de trabalho/aceite mesmo com `status=deleted_verified` e snapshot preservado.
- `needs_owner_intervention`: falha antes de postflight, perda SSH, prova incompleta, API ambígua, custo/tempo incerto ou falha de cleanup. Nenhum DELETE/stop/reboot de host por dedução. O owner consulta `controller.jsonl` e os intents, reconcilia identidade e processos por procedimento/autorização separados. A ausência de manifest não prova ausência de recurso. Falha de teste com cleanup verificado permite delete apenas após prova completa, mas não vira teste aprovado.

O guard recebe duração <= restante até 3 h desde `created_at`; entrada é bloqueada quando sobra menos de 45 minutos para o corte interno. A hora 4 é limite de admissão para delete, não mecanismo capaz de vencer uma API/SSH indisponível. Uso real, cobrança e homologação dependem de observação no provedor, não dos testes fake.

## Evidência e testes locais

A cópia automática inclui postflight, samples, batch-results quando existir, PNG/JPEG/WebP/MP4 diretos de `evidence/journey/<run>` e JSON públicos em allowlist fixa (`result.json`, relatórios phase-gate antes/depois do render, histórico API/browser, leitura/visualização do critic, identidades e terminais dos renders A/B). JSON deve ser objeto regular de até 64 KiB e é sanitizado recursivamente por nome de campo senha/password/token/authorization/cookie/secret; `outputKey` e IDs permanecem. PNG/MP4 têm assinatura/hash de identidade conferidos, com limite individual de 200 MiB e orçamento conjunto de 512 MiB. Em `work_outcome=success`, faltas de `result.json`, screenshot W27 real, JSONs de browser, dois MP4s e seus metadados de identidade/terminal são falha de aceite, não prova de cleanup. O browser JSON precisa conter passos `real` e não estar marcado `failed`. Inventário e erros são preservados para revisão humana — **não** constituem aprovação editorial nem inspeção do MP4. Não copiar env, hostkey, `next.log`, logs brutos nem diretórios recursivos. O controller não altera TODO/gates, não cria VM no `--check` e não agenda tarefa.

    python -m unittest discover -s tests/ops -p test_disposable_controller.py -v
    python -m unittest discover -s tests/ops -p test_disposable_contract.py -v

Estes testes são locais com API/SSH/fake host e contrato real watchdog/guard. Não provam cloud-init, DO, preço vivo, Task Scheduler, SSH real, Linux/FFmpeg, E2E editorial nem exclusão remota. Probe de Task Scheduler sob usuário interativo não prova sobrevivência após logout. Para a rodada supervisionada expressamente autorizada acima, exigem-se revisão, probe independente do chat, Windows ligado/logado, compatibilidade dos pins no venv local, config real privada e gates anteriores verdes. A homologação e a exclusão reais continuam dependentes da execução e do readback no provedor; aprovação local ou autorização não as substituem.
